# 第七课：异常、重试与执行恢复

配套实验：[retry_resume_demo.py](../retry_resume_demo.py)。本课用一个本地模拟数据源制造临时失败，观察自动重试、异常传播以及 checkpoint 恢复，不依赖外部服务。

## 1. 先分清三种“再执行”

| 机制 | 触发原因 | 谁安排下一次执行 |
| --- | --- | --- |
| 业务循环 | 证据不足，需要继续搜索等业务判断 | 节点与条件边 |
| 自动重试 | 节点抛出了策略允许重试的异常 | RetryPolicy |
| 失败后继续执行 | 调用已报错退出，后来准备继续未完成工作 | 调用方使用 checkpoint |

循环中的一次正常结果，与节点异常导致的失败尝试，应分别理解。临时读取失败可以重试，输入不合法通常需要先修正，原样重做并不一定有帮助。[依据：Thinking in LangGraph 的错误分类](https://docs.langchain.com/oss/python/langgraph/thinking-in-langgraph)

## 2. 本课使用的图

```mermaid
flowchart LR
    S([START]) --> P[prepare：准备任务]
    P --> F[fetch：读取数据]
    F --> D[finish：处理完成]
    D --> E([END])
```

只有 fetch 配置了自动重试。图中没有额外画一条 fetch 回到自身的边，因为 RetryPolicy 在节点尝试这一层安排重试。

## 3. 配置节点重试策略

本课定义 `TemporaryReadError` 表示模拟的临时读取异常，并显式指定只重试这个类型：

```python
from langgraph.types import RetryPolicy

builder.add_node(
    "fetch",
    fetch,
    retry_policy=RetryPolicy(
        max_attempts=3,
        initial_interval=0.01,
        jitter=False,
        retry_on=TemporaryReadError,
    ),
)
```

| 参数 | 本例含义 |
| --- | --- |
| max_attempts=3 | 最多尝试三次，包含第一次，因此最多额外重试两次 |
| initial_interval=0.01 | 第一次重试前等待 0.01 秒，为了让实验快速完成 |
| jitter=False | 关闭等待间隔的随机抖动，便于观察 |
| retry_on=TemporaryReadError | 仅对该异常类型及其子类应用重试 |

未覆盖的 backoff_factor 使用默认值 2，等待间隔随重试增加。实际业务需要根据服务情况设置间隔；本例的短间隔仅用于教学。[依据：官方 RetryPolicy 参数](https://docs.langchain.com/oss/python/langgraph/fault-tolerance)

不要理解成“框架会重试所有异常”。默认策略有自己的异常过滤规则，本例通过 retry_on 明确指定实验边界。

## 4. 实验一：自动重试成功

运行：

```powershell
python -B -X utf8 retry_resume_demo.py
```

第一组设定数据源只在第一次读取时失败，实际顺序是：

```text
prepare：第 1 次
fetch：第 1 次 → 抛出 TemporaryReadError
fetch：第 2 次 → 返回数据
finish：第 1 次
```

prepare 没有重跑，finish 也没有在失败尝试后提前运行。自动重试重新调用的是 fetch 节点，成功返回后图才继续。

本例使用外部的 counts 字典记录累计调用次数，同时模拟数据源前几次不可用。这个字典是进程内的实验装置，不属于 State，也不会被 Checkpointer 保存；它不是生产环境的持久化重试计数方案。

## 5. 实验二：重试耗尽后再继续

第二组设定前三次 fetch 调用都失败，第四次可用。

第一次 invoke 内部发生三次尝试后，异常传给调用方。本实验没有配置额外的 error_handler，因此不会自动进入其他恢复分支。

失败后保存的内容为：

```text
status: prepared
payload: ""
next: ('fetch',)
调用次数: prepare=1, fetch=3, finish=0
```

prepare 的结果已经保存；fetch 没有成功返回数据，finish 尚未执行。稍后，使用原有图对象、原有存储以及相同 thread_id：

```python
result = graph.invoke(None, config)
```

本次恢复时，fetch 累计第 4 次调用成功，随后 finish 运行。prepare 仍然只调用过一次。

这展示了 checkpoint 在失败后继续执行中的作用；若故障原因仍存在，继续执行依然可能失败。恢复并不会替你修复数据源或业务逻辑。[依据：官方 Checkpointers 的容错说明](https://docs.langchain.com/oss/python/langgraph/checkpointers)

也能看出 max_attempts 并非整个 thread 生命周期的累计调用上限：自动尝试耗尽后，调用方仍可以在之后继续未完成的执行。业务若需要全流程累计预算，应单独设计。

## 6. 和人工中断恢复有什么区别？

| 当前情况 | 输入形式 | 目的 |
| --- | --- | --- |
| 上一轮已完成，需要处理新输入 | `graph.invoke(new_input, config)` | 提交新的状态输入并开始下一轮 |
| 节点正在等待 interrupt 回复 | `graph.invoke(Command(resume=value), config)` | 将 value 传回对应的 interrupt |
| 本课异常退出后，继续已有未完成工作 | `graph.invoke(None, config)` | 从保存的执行上下文继续 |

第三课的恢复值属于外部输入；本课继续执行不需要给 interrupt 提供值，因为没有使用 interrupt。两者都依赖正确的 thread 和可访问的 checkpoint，但处理的是不同的等待原因。

本课使用 InMemorySaver，在同一个进程中完成实验；没有验证进程退出后的恢复。跨重启需要持久化存储，以及能够重新构建的图与外部依赖。

## 7. 为什么错误不能随便吞掉？

如果节点捕获了临时异常，却返回一个普通字典：

```python
try:
    data = read_source()
except TemporaryReadError:
    return {"payload": "读取失败"}
```

运行时看到的是一次正常返回，不会因为字符串里写着“失败”就触发 RetryPolicy。下一步是否继续，应由你设计的状态和条件边决定。

两种做法都有用途：

- 希望运行时对异常自动重试：让符合策略的异常抛出。
- 希望把错误交给模型或业务分支处理：明确返回错误状态，并设计对应路由。

上面是说明机制的伪代码，read_source 尚未实现；完整实验没有把失败字符串伪装成成功数据。

## 8. 重试与副作用：为什么需要幂等？

假设一个节点先写入外部系统，再因为后续代码失败而抛出异常。整个节点重跑时，前面的写入也可能再次发生。

Checkpoint 记录图的执行状态，不会自动撤销外部系统已经完成的操作。返回失败与外部操作完全没发生，并不是同一件事。

因此，对写库、发消息等操作，应结合业务使用稳定的操作 ID、唯一约束或接收方去重等方式，让重复调用得到可接受的效果。拆分节点可以缩小重做范围，但不能单凭拆节点保证任意故障下的副作用恰好发生一次。

这与第三课中 interrupt 前的代码可能重跑，是同一个设计问题：**一段代码被重新进入时，重复执行的结果是否可控？**

## 9. 和 LangChain 的重试层次对照

LangChain 的模型集成也可能提供请求重试参数，例如 ChatOpenAI 的 max_retries。它控制模型请求层面的重试；LangGraph 的 RetryPolicy 则重新执行整个节点函数。[依据：ChatOpenAI 配置示例](https://docs.langchain.com/oss/python/integrations/chat/openai)

如果一个节点内有多个操作，而且模型客户端也会自行重试，实际底层请求次数会受到多层机制共同影响。不能把节点 max_attempts=3 直接理解为整个应用最多发送三个请求。

## 10. 验证结果与练习

| 场景 | prepare 累计次数 | fetch 累计次数 | finish 累计次数 | 结果 |
| --- | --- | --- | --- | --- |
| 第一次临时失败，第二次成功 | 1 | 2 | 1 | completed |
| 三次失败，异常传出时 | 1 | 3 | 0 | 保留 prepared 状态 |
| 同一 thread 继续执行后成功 | 1 | 4 | 1 | completed |

验证记录：2026-10-21，两组实验已在当前 Python 3.13.7、LangGraph 1.2.4 环境运行，结果与上表一致。

2. 将 max_attempts 改为 1，观察一次异常是否直接传到调用方。
3. 在 fetch 中将异常类型改为 ValueError，观察显式设置 retry_on 后还会不会重试。
